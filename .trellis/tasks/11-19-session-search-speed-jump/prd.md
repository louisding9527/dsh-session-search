# 会话搜索提速与命中定位

## Goal

1. 把侧边栏会话搜索从「每次全文解压扫描」改成可增量复用的快路径，缩短等待并消除宿主卡顿。
2. 点击搜索结果后，落到命中关键字所在的句子（当前落到会话末尾），并给出可见的高亮。

## Background（本机实测，2026-11-19）

环境：2,166 个会话文件、317 MB、单项目目录占 2,037 个文件；搜索范围 UI 固定为 `all`。

| 场景 | 现状 |
|---|---|
| 枚举会话文件 | 257 ms，同步 `readdir` + `stat`，跑在宿主事件循环里（`lib/http.js:85`、`lib/sessions.js:41-83`） |
| UI 形状查询（limit 25、每会话 3 段） | 常见词「会话」690 ms；生僻词「dsh-session-search」/「zstdDecompressSync」约 2.9–3.1 s |
| 6 个子进程启动 | 约 153 ms（每次查询都重新 spawn，`lib/pool.js:73`） |
| 全量解压 + `JSON.parse` | 单线程约 15 s，6 路并行约 3 s；实际可检索文本只有约 44 MB |
| 过期查询 | 浏览器 abort 后宿主扫描不停止：路由只传 `limit`，没有传 `signal`（`lib/http.js:92-97`；工具路径反而传了 `exec.signal`，`lib/index.js:260`） |

跳转现状：`pickResult` 只调用 `uiWorkspace.openSession(sessionId)`（`lib/client.js:298-311`）。DSH 的 `openSession(target)` 只接受会话目标，没有消息/seq 锚点（app.asar `dsh-client-ui-workspace/src/client/navigation.ts:46,294`）；聊天视图无保存位置时默认跟随末尾（`use-chat-reading.ts` 的 `restore()`），所以打开后停在会话末尾。聊天行有稳定 DOM 标记 `data-chat-node-key`（`ChatNodeSeat.tsx:160`），滚动位置存储不对外暴露。

已排除的现成方案：DSH 自带 `ctx.sessionQuery` + SQLite FTS5 在默认装配里 `openAt: never`、`:memory:`（app.asar `dsh-web-app/cordis.patch.yml`）；且 `unicode61` 只匹配 token，不做任意子串，中文关键词不可用（`dsh-session-query-sqlite/README.md`）。因此仍需自建子串检索，但可以自建文本缓存。

## Requirements

- **R1 增量文本缓存（已定：方案 A + 每轮结束自动补缓存）**：为每个会话文件生成可检索文本缓存（含 `seq`、`turn`、`time`、`role`、文本），按源文件 `mtime+size` 失效；缺失或过期时由现有解压路径重建并写回。缓存只含 `messages` 模式文本；`all` 模式保留原扫描作为兜底。
  - **R1a 轮次结束触发**：宿主监听 `ctx.on('session/event', …)`，遇到 `turn/end` 后在后台对该会话做增量同步（从缓存记录的帧边界偏移继续读，追加新行）；同步失败或文件尚未落盘时，下一次查询继续补齐。
  - **R1b 历史存量**：插件安装前已存在的会话在首次被搜索到时先用整文件扫描返回结果，再排进低优先级后台队列建缓存；不要求启动时全量重建，也不让冷查询先等建缓存。
  - **R1c 不阻塞**：缓存重建/增量同步都放到 worker 或子进程，宿主事件循环只做排队。
- **R2 查询快路径**：有缓存时只读缓存并做子串匹配，不再解压 `.zstd`、不再 `JSON.parse` 全量事件；常见词按新到旧提前收工。
- **R3 宿主不卡顿**：枚举/`stat` 与缓存扫描移出宿主主线程或做短 TTL 缓存，单次同步阻塞目标 ≤50 ms。
- **R4 取消生效**：客户端 abort（继续输入、关闭弹窗）必须传到宿主，终止对应 worker/子进程；不产生并行堆积的过期扫描。
- **R5 跳转定位（已定：轨道优先，自动翻页兜底）**：点击结果（或单条片段）打开会话后，自动定位到命中文本所在句子，居中显示并做短时高亮。命中轮次未加载时，先激活 DSH 轮次轨道翻页到该轮；轨道不可用则自动上滚触发历史加载，最多 5 s。跳转目标用缓存里的 `turn`/`seq` 与文本双重定位，不依赖“滚到最末”。
- **R6 降级**：上述路径仍失败时，保持会话已打开，给出明确提示「已打开会话，但未定位到命中」；不静默停在末尾。
- **R7 兼容**：`session_search` / `session_read` 工具行为与参数不变；HTTP 路由只增字段不破坏现有响应；缓存目录独立、可删、有容量上限。

## Acceptance Criteria

- [ ] 2,166 文件基线下，缓存命中后常见词查询 ≤300 ms、生僻词 ≤800 ms（脚本实测，连续 5 次取中位数）。
- [ ] 安装/启用后，任一进行中的会话在 `turn/end` 后下一个查询即可命中该轮新内容（无需再次全量解压）。
- [ ] 首次遇到未缓存的历史文件时允许接近现状耗时，但完成后缓存落盘；第二次同一查询走快路径。
- [ ] 缓存增量同步不重读整文件：一次 `turn/end` 后的同步读取量只与被追加的帧大小相当。
- [ ] 宿主无单次 >50 ms 的同步文件枚举；搜索期间 UI 不出现明显卡顿。
- [ ] 输入新关键词后 200 ms 内旧查询的子进程全部退出（可通过进程数观察）。
- [ ] 点击命中的片段后 1.5 s 内视口出现该句并居中；高亮至少可见 1.5 s。
- [ ] 命中位于未加载历史时：轨道可用则在 5 s 内落到该轮并定位句子；轨道不可用则自动上滚在 5 s 内定位；两者都失败才出现提示，且会话保持打开。
- [ ] 固定查询集（中英文各若干）在改动前后命中会话集合一致（允许排序变化）。
- [ ] 向会话追加事件后，下一次查询能命中新内容（缓存按 `mtime+size` 失效）。

## Out of Scope

- 引入常驻倒排索引 / SQLite FTS / 向量检索。
- 修改 DSH 本体或给 `openSession` 增加锚点参数。
- `include=all`（工具调用、工具结果、思考过程）的缓存提速；先保证默认 `messages` 路径。
- 重新设计弹窗视觉与交互（除定位提示与高亮外）。
- 改变默认搜索范围（仍为 `all`）；“默认只搜当前项目”另开任务评估。
- 缓存加密；缓存与 `~/.dsh/sessions` 同级敏感，按本机文件权限保护。

## Decisions

- **D1 速度方案 = A + 每轮结束自动缓存**（2026-11-19 用户确认）：增量文本缓存作为快路径；`turn/end` 后后台增量同步；历史存量按需建。冷存量首次仍接近现状耗时，但正常使用下缓存会被持续预热。
- **D2 深历史定位 = 轨道优先，自动翻页兜底**（2026-11-19 用户确认）：允许页面跳动，最长 5 s；失败才提示。接受对 DSH 聊天 DOM/轮次轨道的耦合，但必须带特性探测和降级。
- **D3 索引方案不纳入本期**（2026-11-19 用户确认）：自建倒排、SQLite FTS、向量检索均不做。理由是缓存命中后最坏 284 ms，索引只能再省约 0.2 s，却带来 150–250 MB 磁盘、失效/重建逻辑或 embedding 依赖；向量属于“语义召回”另一目标。
  - 重评阈值：会话数 >5,000、可检索文本 >300 MB、或热查询 p95 >1 s。
  - 若日后要“不记得原词也能找”，单开语义搜索任务评估 embedding 服务、成本与隐私。
